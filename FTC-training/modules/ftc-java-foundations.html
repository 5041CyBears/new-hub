Module Goals

By the end, students should be able to:

  • Explain how the FTC SDK, TeamCode, OpModes, hardwareMap, telemetry, and gamepads fit together.
  • Write a basic Java LinearOpMode that maps hardware, waits for start, loops safely, and updates outputs.
  • Use variables, methods, conditionals, classes, and constants to make robot code understandable.
  • Separate hardware configuration problems from Java logic problems.
  • Use telemetry, comments, version control, and incremental testing to debug code safely.

Big Picture

The system at a glance

FTC SDK

The SDK provides the Robot Controller framework, hardware APIs, OpMode system, Driver Station communication, samples, and season-specific software support.

TeamCode

For Android Studio teams, custom robot code belongs in the TeamCode module rather than editing core SDK framework files.

OpMode

An OpMode is a Driver Station-selectable robot program. LinearOpMode is a common beginner-friendly structure with runOpMode(), waitForStart(), and an active loop.

hardwareMap

The hardware map connects a configured robot device name to a Java object. If the name/type/port configuration is wrong, otherwise-correct code can still fail.

Telemetry

Telemetry is a programming instrument panel. Show state, sensor values, commands, errors, and intermediate calculations rather than only 'code running.'

Gamepads

FTC exposes gamepad inputs through SDK gamepad objects. Read controls intentionally and convert raw inputs into clear robot actions.

Core Knowledge

Important concepts

Types & Variables

Use meaningful names and appropriate types. Constants for dimensions, limits, and gains make tuning safer than scattered magic numbers.

Methods

Extract repeated operations and meaningful actions into methods. A method name like setIntakePower() communicates intent better than duplicated motor calls.

Conditionals

Use if/else when robot behavior depends on input or state. Keep conditions readable and avoid deeply nested logic where a state machine would be clearer.

Classes

Classes can represent subsystems, helpers, geometry, or data. Do not create abstraction just for its own sake; use it to reduce duplication and make ownership clear.

Loop Discipline

Avoid long blocking sleeps or loops inside TeleOp. The robot must repeatedly read inputs, update logic, write outputs, and remain responsive.

Git & Backups

Commit known-good states before major changes. Version control turns experimentation from a risky overwrite into a recoverable engineering process.

Practical Advice

What students should actually do

  • Start every new mechanism with the smallest code that can safely prove one behavior.
  • Name devices by mechanism and function, not by whichever port they happened to use during the first prototype.
  • Keep robot dimensions, gains, speed limits, and setpoints in obvious constants or configuration structures.
  • Print both commanded and measured values when debugging closed-loop behavior.
  • Use helper methods for repeated behavior but keep them small enough to understand.
  • Never test unknown code with the robot raised, unrestrained, or near people.
  • Commit working code before refactoring or adding a major feature.
  • When importing SDK updates, follow official migration instructions rather than manually replacing random Gradle files.

Competition Habits

Make the system repeatable and recoverable

Make state visible

Use labels, telemetry, logs, marks, checklists, or diagrams so students can tell what is happening without guessing.

Test failure modes

Create controlled bad conditions and practice safe recovery instead of testing only perfect operation.

Train backups

More than one student should know how to operate, explain, troubleshoot, and repair the system.
