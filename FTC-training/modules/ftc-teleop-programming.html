Module Goals

By the end, students should be able to:

  • Turn gamepad input into responsive, predictable, and driver-friendly robot behavior.
  • Use deadbands, scaling, toggles, edge detection, and state machines appropriately.
  • Separate driver intent from mechanism implementation so controls remain maintainable.
  • Build safe interlocks and recovery controls without making the robot impossible to operate.
  • Tune controls through structured driver practice and logged/observed failure cases.

Big Picture

The system at a glance

Drive Inputs

Map sticks intentionally, account for FTC gamepad conventions, apply deadbands where needed, and decide whether drivers need full speed all the time.

Buttons

A button is a Boolean input, but the desired behavior may be hold, toggle, press-once, release, or start a state transition. Define that behavior explicitly.

Mechanism States

Rather than scattering servo positions and motor powers across button logic, define meaningful states such as STOWED, INTAKING, TRANSFERRING, and SCORING.

Interlocks

Prevent damaging combinations such as extending before an arm clears the frame. Interlocks should protect hardware while still giving drivers a deliberate recovery path.

Feedback

Driver-facing telemetry/indicators should answer: What state is the robot in? Is the action complete? What failed?

Practice Loop

Controls are an interface between software and a human under pressure. Driver feedback is engineering data.

Core Knowledge

Important concepts

Deadband

Small joystick noise near zero can cause unwanted drift. Ignore a small center region, then optionally rescale the remaining range.

Input Shaping

Squared/cubed stick response can give finer low-speed control while retaining full output. Test with the actual driver rather than assuming one curve is best.

Edge Detection

For a toggle, act once when a button changes from not-pressed to pressed. If you toggle every 20 ms while held, the state will flicker unpredictably.

Non-Blocking Logic

Do not freeze TeleOp waiting for a mechanism. Start an action, continue looping, and update its state until complete or canceled.

Manual Overrides

Automated mechanisms still need a safe way to recover from sensor faults, jams, or unusual geometry.

Operator Load

Do not make drivers remember dozens of arbitrary combinations. Group controls by role and match sequence.

Practical Advice

What students should actually do

  • Ask drivers what information they need without looking away from the field.
  • Keep the most frequent actions on the easiest controls to reach.
  • Use consistent direction conventions: positive stick should produce an intuitive robot response.
  • Create named mechanism states instead of repeating raw servo/motor numbers across button handlers.
  • Test controls after every mechanical geometry change because safe setpoints may have changed.
  • Practice jam recovery deliberately; do not wait for a tournament to discover the override is inaccessible.
  • Record driver complaints as specific situations: 'hard to align at 20 cm' is more useful than 'drive feels bad.'
  • Freeze control mappings before an event unless a change fixes a real problem and is re-practiced.

Competition Habits

Make the system repeatable and recoverable

Make state visible

Use labels, telemetry, logs, marks, checklists, or diagrams so students can tell what is happening without guessing.

Test failure modes

Create controlled bad conditions and practice safe recovery instead of testing only perfect operation.

Train backups

More than one student should know how to operate, explain, troubleshoot, and repair the system.
