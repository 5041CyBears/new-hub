Module Goals

By the end, students should be able to:

  • Explain the FTC VisionPortal, vision processors, cameras, AprilTag detection, and robot/camera coordinate relationships.
  • Configure a vision pipeline intentionally for resolution, exposure, field of view, and processing load.
  • Use AprilTag detections for identification, alignment, or localization without blindly trusting every detection.
  • Account for camera mounting offset and transform measurements into robot-relevant information.
  • Design fallbacks for no-target, ambiguous, stale, or low-quality vision data.

Big Picture

The system at a glance

VisionPortal

FTC VisionPortal is the SDK interface used to manage camera input and vision processors such as AprilTag processing. A portal can be created with defaults or configured with a Builder.

AprilTags

AprilTags encode IDs and provide geometric features that can support target identification and pose estimation. The current season's built-in tag library is provided through the SDK where applicable.

Camera Calibration

Accurate 3D measurements depend on camera intrinsics appropriate to the device/resolution. If you change camera or resolution, verify the calibration assumptions.

Exposure & Blur

A bright but motion-blurred image may be worse for detection than a darker sharp one. Exposure and gain should be tuned for the robot's motion and field lighting.

Camera Transform

The camera is not usually at the robot center. Measure its position/orientation relative to the robot so camera observations can be converted into robot geometry.

Quality Checks

A detection is data, not truth. Check target ID, ambiguity/quality indicators where available, age/timestamp, range, and whether the result is physically plausible.

Core Knowledge

Important concepts

Resolution Tradeoff

More pixels can improve target detail but increase bandwidth/processing. Use enough resolution for the task rather than maximizing it by default.

Multiple Processors

VisionPortal can support multiple processors, but each adds computation. Enable only what is needed for the current task when performance matters.

Field Coordinates

Define one field coordinate convention and one robot coordinate convention. Document rotations and transforms; many vision bugs are actually coordinate-frame bugs.

Target Loss

Vision-based aiming must handle no target. Freeze a safe last value briefly only if appropriate, time it out, and give the driver feedback.

Localization Fusion

Vision can correct accumulated odometry error, but fusing an outlier can make localization worse. Validate measurements before applying corrections.

Lighting Tests

Practice field lighting may differ from event lighting. Test a range of exposure settings and avoid algorithms that depend on one perfect brightness.

Practical Advice

What students should actually do

  • Rigidly mount the camera; a flexing camera mount changes the transform and invalidates calibration assumptions.
  • Measure the camera position and orientation on the actual robot, not only in CAD.
  • Tune exposure while the robot is moving at realistic speed.
  • Log detection ID, range/bearing, ambiguity/quality, timestamp, and whether your code accepted or rejected the measurement.
  • Add obvious telemetry when the target is lost or data is stale.
  • Do not let one vision measurement instantly command a violent mechanism movement; filter/control the response appropriately.
  • Test from near/far distances and shallow/steep viewing angles.
  • Keep a non-vision fallback for critical match actions where practical.

Competition Habits

Make the system repeatable and recoverable

Make state visible

Use labels, telemetry, logs, marks, checklists, or diagrams so students can tell what is happening without guessing.

Test failure modes

Create controlled bad conditions and practice safe recovery instead of testing only perfect operation.

Train backups

More than one student should know how to operate, explain, troubleshoot, and repair the system.
