Module Goals

By the end, students should be able to:

  • Explain the responsibilities of Robot, RobotContainer, subsystems, commands, triggers, and the CommandScheduler.
  • Structure Java robot code so hardware ownership is separated from high-level robot actions.
  • Use command requirements to prevent conflicting code from controlling the same subsystem.
  • Use default commands, triggers, command factories, and composition tools such as sequence, parallel, race, and deadline.
  • Trace command initialization, repeated execution, finish/interruption, and scheduler behavior.
  • Recognize common architecture problems such as duplicated hardware access, giant commands, hidden side effects, and unsafe command reuse.

Subsystems

Make the subsystem the single source of truth for a robot capability

public class Shooter extends SubsystemBase { private final MotorController motor = ...; public void setVelocity(double rpm) { ... } public boolean atSpeed() { ... } public void stop() { ... } @Override public void periodic() { /* log sensors/state */ } }

Keep unit conversions and hardware-specific details close to the subsystem. Commands should not need to know CAN IDs or encoder conversion factors.

Commands

Commands describe a temporary action or goal

Command owns

  • when action starts
  • what goal is requested
  • when it ends
  • cleanup on interruption

Command should not own

  • duplicate motor objects
  • global state unrelated to its action
  • hidden controller bindings
  • unbounded blocking loops
Scheduler

The CommandScheduler arbitrates who gets to use each subsystem

Ordinarily the scheduler runs once per robot loop (about 20 ms), polls triggers, schedules commands, calls subsystem periodic methods, executes scheduled commands, and ends finished/interrupted commands.

Practical Advice

Write robot code for the pit at 9:30 PM, not just for the first programmer

  • Prefer short commands with obvious requirements and clean end behavior.
  • Use subsystem methods named after intent: setHeight(), runIntake(), stop()—not dozens of raw motor calls throughout commands.
  • Build autonomous from the same tested commands used elsewhere when practical.
  • Use factories/lambdas for parameterized commands instead of keeping mutable command singletons with stale state.
  • Log current goals, measurements, and command state so a student can diagnose why the robot is doing something.
  • Review scheduler interruptions deliberately. “Why did my command stop?” is often a requirement conflict, trigger release, or finish condition.
