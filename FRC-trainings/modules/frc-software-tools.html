Module Goals

By the end, students should be able to:

  • Identify the major software used to program, deploy, run, configure, and troubleshoot an FRC robot.
  • Explain the role of WPILib, the annual WPILib installer, and the WPILib-specific copy of Visual Studio Code.
  • Use the 2027 FIRST Driver Station as the center of robot enable/disable, controller, match-state, and communications workflows.
  • Explain how the 2027 Systemcore changes controller imaging, deployment, networking, and diagnostic workflows.
  • Choose between Elastic, AdvantageScope, and Glass for different dashboard and debugging jobs.
  • Recognize common vendor utilities such as REV Hardware Client 2 and Phoenix Tuner X.
  • Understand where autonomous tools, vision tools, simulation, Git/GitHub, and vendor dependencies fit into the software stack.
  • Build a practical competition-ready software workflow instead of installing tools only when something breaks.
Important 2027 Note

FRC software is in a major control-system transition

This module is updated for the 2027 preseason as of September 2026.

The 2027 software stack is still being refined before kickoff. Always check the current WPILib documentation and FIRST season documentation before competition.

2026 and Earlier

  • roboRIO / roboRIO 2.0 controller
  • NI-based FRC Driver Station
  • roboRIO Imaging Tool
  • OpenMesh or VH-109-era transition networking

2027 Direction

  • Systemcore replaces roboRIO as the competition robot controller.
  • A new FIRST Driver Station supports Systemcore and newer WPILib features.
  • Systemcore OS updates use its web interface and .llupdate files.
  • WPILib has major API and tool changes for the new control system.
Current official references: WPILib — New for 2027 and WPILib — The 2027 FIRST Driver Station.

WPILib Installer

The annual installer creates the FRC development environment

WPILib Libraries

Robot-side APIs for motors, sensors, command frameworks, geometry, kinematics, logging, simulation, and more.

Build Toolchain

Java/C++ compiler support, Gradle/GradleRIO, JDK, native libraries, and deploy tooling.

Desktop Tools

Tools such as Glass, SysId, AdvantageScope, Elastic, OutlineViewer, simulation tools, and documentation.

Practical rule: install the WPILib release for the season you are programming. FRC projects, vendor libraries, controller software, and desktop tools are version-sensitive.

The 2027 installer documentation says the package includes VS Code, Gradle, Java tooling, WPILib dependencies, desktop tools, extensions, and offline documentation. WPILib Installation Guide
Visual Studio Code

Use the WPILib copy of VS Code

What students do here

  • Create or import robot projects.
  • Edit Java, C++, or Python robot code.
  • Build and deploy to Systemcore.
  • Install and update vendor dependencies.
  • Run simulation.
  • View robot console output and deploy errors.
  • Use WPILib examples and documentation.

Why the special copy?

The WPILib installer sets up a dedicated VS Code environment with the correct WPILib extension and matching development tools.

Do not assume your normal personal VS Code install is equivalent.

VS Code Practical Habits

Know the WPILib commands instead of hunting through menus

Commands worth memorizing

  • Create a New Project
  • Build Robot Code
  • Deploy Robot Code
  • Simulate Robot Code
  • Manage Vendor Libraries / Dependency Manager
  • Set Team Number
  • Import a previous-year project

Good workflow

  • Build before walking to the robot.
  • Read the first meaningful compiler error, not just the last red line.
  • Commit working code before a risky refactor.
  • Do not update libraries in the queue at competition.
  • Keep one known-good deployable branch/tag.

2027 Systemcore

The robot controller is now part of the software workflow

What Systemcore does

  • Runs your deployed robot program.
  • Hosts robot networking and web-based configuration.
  • Connects to CAN, USB, Ethernet, I2C, and reconfigurable I/O.
  • Provides onboard status information and an IMU.

Programmer responsibilities

  • Keep its OS version compatible with the team's software stack.
  • Know how to reach its web dashboard.
  • Know the team number and robot network.
  • Do not update it immediately before an important match.
The 2027 Systemcore is a Raspberry Pi Compute Module 5-based controller with built-in robotics I/O and networking. Systemcore Introduction
Systemcore Updating / “Imaging”

Do not use the old roboRIO Imaging Tool on a Systemcore

1Download

Get the correct current .llupdate release file.

2Connect

Connect to Systemcore by USB or network.

3Open Web UI

Open the Systemcore dashboard, normally at robot.local.

4Update

Use the Configure & Update area to select and flash the update.

5Verify

Confirm the update succeeds, then reconnect and test communications.

Preseason hardware note

Some older alpha/beta Systemcore images may require the Limelight Hardware Manager for an initial update. Follow current official instructions for the hardware version in front of you.

Legacy Robot Software

Know what still belongs to older roboRIO robots

roboRIO Imaging Tool

Still relevant if your team maintains a 2026-or-earlier roboRIO practice robot. It is not the normal Systemcore update method.

NI FRC Game Tools / NI Driver Station

Important for roboRIO-era systems. For 2027 Systemcore competition development, learn the new FIRST Driver Station workflow.

Practical advice: label practice laptops and robots by control-system generation. “This worked on our old roboRIO robot” does not mean the same tool is correct for Systemcore.

Driver Station Practical Advice

Treat the drive laptop as competition equipment

Do

  • Use a dedicated driver laptop when possible.
  • Prefer a reliable built-in Ethernet port.
  • Keep Windows, FRC software, and drivers intentionally managed.
  • Lock controller order and label USB devices/cables.
  • Test a full match cycle before the event.
  • Know how to access Driver Station logs.

Avoid

  • Discord, game launchers, cloud sync, CAD updaters, or unnecessary background software while driving.
  • Windows updates in the queue.
  • Cheap unknown USB/Ethernet adapters.
  • Changing controller USB ports between matches.
  • Installing new robot software while queued for a match.
WPILib's current Driver Station best-practices guide emphasizes dedicated, reliable hardware and minimizing background software. Driver Station Best Practices

Choosing a Dashboard · New for 2027
Elastic

Keep the driver dashboard simple

Good driver data

  • Auto selection
  • Mechanism ready/not-ready
  • Piece detected
  • Critical fault alert
  • Match-relevant status

Bad driver dashboard habits

  • Twenty tiny gauges
  • Raw encoder values
  • Every motor temperature
  • Information the driver cannot act on
  • Layouts changed on event morning

A drive team's eyes belong on the field. The dashboard should answer a small number of important questions instantly.

Vendor Device Utilities

Your code library and your hardware configuration tool are not the same thing

REV Hardware Client 2

  • Detect compatible REV devices.
  • Update firmware.
  • Configure devices.
  • Back up and restore device data.
  • View telemetry and test hardware.

REV says teams using REV ION products with REVLib 2026 or newer should use REV Hardware Client 2.

Phoenix Tuner X

  • Discover CTRE devices.
  • Update firmware.
  • Set CAN IDs and names.
  • Configure and test CTRE hardware.
  • Manage Phoenix licensing/features where applicable.

Phoenix 6 is the current CTRE software family for modern FRC CTRE devices.

Competition habit

Record device firmware versions and CAN IDs before events. Do not update every motor controller because an updater says “new version available” unless the team has time to rebuild, reboot, and fully retest.

Network & Radio Configuration

The 2027 workflow is increasingly web-based

VH-109 Radio

Current WPILib guidance configures VH-109 radios through their web page, normally reached at radio.local while directly connected.

Robot Simulation

Test logic before the robot is available

Simulation can help with

  • Command scheduling
  • Autonomous sequencing
  • Dashboard and NetworkTables behavior
  • Basic drivetrain/mechanism models
  • Input handling

Simulation cannot prove

  • Real mechanism friction
  • Bad wiring
  • Loose chains/belts
  • Real sensor mounting errors
  • CAN wiring reliability

Use WPILib: Simulate Robot Code, not the generic VS Code “Run” button. Some vendor libraries may have limited simulation support.

Specialized WPILib Tools

Useful tools programmers should recognize

SysId

Collects mechanism data for characterization and feedforward/control-system analysis.

OutlineViewer

Inspect NetworkTables topics/values when a dashboard is hiding too much detail.

Data Log Tools

Review and process robot logs instead of relying only on live console text.

Autonomous Planning Software

Path tools generate plans; robot code still has to execute them correctly

Choreo

A time-optimal trajectory planning tool listed directly in WPILib documentation. Supports swerve and differential drive trajectories and a robot-side ChoreoLib.

PathPlanner

A widely used FRC autonomous/path planning application with a companion PathPlannerLib vendor dependency.

2027 change

WPILib has removed PathWeaver for 2027 and points teams toward modern options such as Choreo, PathPlanner, or Bline.

Practical advice: keep path files in version control, verify field coordinates, test alliance flipping/mirroring, and validate autonomous routines on the real robot before relying on them in a match.

Vision Software

Vision usually has its own configuration application or web interface

PhotonVision

Free FRC vision-processing software with a web UI and PhotonLib vendor dependency for reading vision results in robot code.

Limelight

Limelight devices use browser-based configuration for pipelines, cameras, networking, targeting, and diagnostics. Systemcore is also made by Limelight but has its own controller role.

Do not treat “vision works in the web UI” as proof that robot code is using it correctly. Verify timestamps, transforms, target ambiguity, coordinate systems, and how measurements are fused into robot state estimation.

Git & GitHub

Version control is not optional on a serious programming team

Git gives you

  • A history of working code.
  • Branches for experiments.
  • The ability to compare exactly what changed.
  • A recovery path when a change breaks the robot.

GitHub gives the team

  • A shared remote repository.
  • Pull requests and code review.
  • Issues and documentation.
  • Offsite backup and collaboration.

Competition rule of thumb

Commit before a major pit change. If the robot worked in the previous match, you should be able to identify and reverse the exact software change made since then.

Pit Troubleshooting Order

Diagnose layers instead of changing random things

1Power

Is the controller/device actually powered?

2Network

Can the laptop communicate with the robot?

3Robot Code

Is code running without crashing?

4CAN / Device

Is the device present with the expected ID/firmware?

5Inputs

Are controllers and sensors reporting what code expects?

6Logic

Only then dig into commands, states, and algorithms.

Most expensive troubleshooting mistake: rewriting code when the real problem is power, networking, firmware, an unplugged controller, or the wrong CAN ID.
